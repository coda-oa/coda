# DaisyUI CSS delivery for CODA

## Recommendation

Use the **official Tailwind standalone CLI plus daisyUI’s standalone plugin bundle** as a build-time asset compiler, then serve only its generated CSS through Django staticfiles and WhiteNoise. This is the closest match to daisyUI’s current [Django installation guide](https://daisyui.com/docs/install/django/), which explicitly demonstrates a Node-free standalone executable, and it does not add a frontend dependency to `pyproject.toml`. Keep the compiler, input CSS, and plugin bundle in a build-only location outside `src/coda/apps/static`; generate the sole runtime artifact (for example, `css/tailwind.css`) into that static source directory. Run that build in CI or an image/build stage, before the existing production `collectstatic` step—not as a per-request operation or an implicit network-dependent runtime installation. Tailwind documents the CLI as a zero-runtime build that scans markup and writes static CSS; daisyUI’s standalone/Django guides show the executable-and-plugin-bundle workflow ([Tailwind CLI](https://tailwindcss.com/docs/installation/tailwind-cli), [daisyUI standalone](https://daisyui.com/docs/install/standalone/), [daisyUI Django](https://daisyui.com/docs/install/django/)).

A locked Node CLI build is equally supported and is a good alternative if the project prefers npm’s dependency and lockfile workflow; use `tailwindcss`, `@tailwindcss/cli`, and `daisyui`, with `@import "tailwindcss"; @plugin "daisyui";`, in a build-only Node stage. The CLI runs without a separate bundler. Do not add Node to the Django runtime solely to generate CSS ([Tailwind CLI](https://tailwindcss.com/docs/installation/tailwind-cli), [daisyUI CLI integration](https://daisyui.com/docs/install/cli/)).

## Viable approaches

| Approach | Fit here | Trade-offs |
| --- | --- | --- |
| **Standalone Tailwind CLI + daisyUI bundle (recommended)** | Directly demonstrated by the current official Django integration and requires no Node runtime. | The CLI is a platform-specific executable; the daisyUI plugin/theme `.mjs` bundle must accompany it. Pin compatible release artifacts and verify their provenance/checksums rather than relying on an unpinned “latest” download. The official quick-install script downloads “latest,” so adapt it for reproducible builds instead of copying that detail verbatim ([Django guide](https://daisyui.com/docs/install/django/), [standalone guide](https://daisyui.com/docs/install/standalone/)). |
| **Node Tailwind CLI** | Official, simple CLI workflow; suitable if npm manifests/lockfiles and Node build tooling are acceptable. Build in a disposable build stage and copy only generated CSS to the Django static tree. | Introduces a second dependency-management workflow absent from `pyproject.toml`; Node is only needed for this build, not to serve CSS ([Tailwind CLI](https://tailwindcss.com/docs/installation/tailwind-cli), [daisyUI CLI guide](https://daisyui.com/docs/install/cli/)). |
| **CDN CSS** | Quick prototype or a deliberately limited set of prebuilt daisyUI components. | Not a substitute for generating the project’s detected Tailwind utilities: daisyUI’s CDN documents separate component CSS and notes that variant classes are not included because the full set would be large. It also leaves an external runtime asset dependency. Prefer a generated, locally served stylesheet for this app ([daisyUI CDN](https://daisyui.com/docs/cdn/)). |
| **Vite/PostCSS or another bundler** | Supported when there is a broader frontend bundle/import pipeline to own. | More machinery than needed for the present deliverable: a static CSS file from Tailwind’s CLI already fits Django’s staticfiles/WhiteNoise path. Tailwind documents Vite and PostCSS as supported integrations, but neither is required just to compile CSS ([Tailwind installation options](https://tailwindcss.com/docs/installation)). |

## Build, collection, and serving

CODA’s `STATICFILES_DIRS` points at `src/coda/apps/static`, and its production start script runs `manage.py collectstatic` before Gunicorn (`config/settings/base.py`; `dockerfiles/production/django/start`). Put the generated CSS under that static directory, e.g. `src/coda/apps/static/css/tailwind.css`, while keeping the input stylesheet, standalone executable, and daisyUI plugin bundle outside it so those build-only files do not become collected/public static assets.

The output must exist before `collectstatic`: Django collects files from configured static locations into `STATIC_ROOT`, and WhiteNoise’s configured `CompressedManifestStaticFilesStorage` hashes and compresses static assets. Add a stylesheet link to the shared `base.html` using Django’s `{% static %}` tag (e.g. `{% static 'css/tailwind.css' %}`), not a hard-coded URL. This keeps Django’s manifest URL rewriting in use and leaves CSS under the already configured staticfiles/WhiteNoise delivery path ([Django static files and deployment](https://docs.djangoproject.com/en/6.1/howto/static-files/), [Django deployment](https://docs.djangoproject.com/en/6.1/howto/static-files/deployment/), [WhiteNoise Django guide](https://whitenoise.readthedocs.io/en/stable/django.html)).

For the standalone compiler, use a CSS entry file conceptually like:

```css
@import "tailwindcss" source("../../src/coda/apps");
@plugin "./daisyui.mjs";
```

This assumes an input file at `tools/tailwind/input.css`; the `source()` path is relative to that stylesheet and makes scanning independent of the compiler’s current working directory. The daisyUI Django guide’s local bundle workflow also demonstrates `@plugin "./daisyui.mjs"`; for the Node CLI, install daisyUI as a dependency and use `@plugin "daisyui"` instead ([Tailwind source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files), [daisyUI Django](https://daisyui.com/docs/install/django/), [daisyUI CLI](https://daisyui.com/docs/install/cli/)).

## Template class detection

Tailwind scans source files as plain text; it does not execute Django templates or Python to discover their runtime output. Point source detection at the repository’s template/application source tree, including every template directory that can render Tailwind classes and any Python/JavaScript source that contains class literals passed into rendered markup. Include HTMX partial templates too: those classes must be present at build time even though their HTML is returned later. Tailwind ignores `.gitignore` paths, `node_modules`, CSS, binary files, and certain lock files by default, so explicitly register the source directory when automatic discovery or the working directory could miss it ([Tailwind class detection and `@source`](https://tailwindcss.com/docs/detecting-classes-in-source-files)).

Do not construct utility names through Django interpolation or concatenation, e.g. `bg-{{ color }}-500`; the complete candidate class does not appear in the source and therefore is not generated. Prefer conditional branches or a mapping whose values are complete strings (`bg-red-500` / `bg-green-500`). For finite classes that only exist in runtime data or otherwise cannot be represented in scanned source, add explicit `@source inline(...)` candidates; do not expect Tailwind to inspect the database, a request, or an HTMX response at runtime ([Tailwind dynamic classes and inline sources](https://tailwindcss.com/docs/detecting-classes-in-source-files)).

## HTMX and Shadow DOM

Load the generated stylesheet once from the shared document shell (`base.html`); HTMX fragment markup can then use the same generated class set without adding another stylesheet link per fragment. The CSS must be generated from the full set of server-rendered templates rather than only the initial page ([Tailwind detection model](https://tailwindcss.com/docs/detecting-classes-in-source-files); the app’s shared shell is `src/coda/apps/templates/base.html`).

A document stylesheet does not automatically style elements inside an encapsulated Shadow DOM tree. CODA already has a bridge: `src/coda/apps/static/js/global-styles.js` reads `document.styleSheets`, creates same-document `CSSStyleSheet` objects from their rules, and adopts them into each custom element’s shadow root. Keeping the generated stylesheet as a same-origin local static asset lets this existing bridge expose its compiled Tailwind/daisyUI rules in those roots. Constructed stylesheets must belong to the same parent document as the shadow root, and `adoptedStyleSheets` applies their rules in the shadow subtree ([CSSOM adopted stylesheets](https://drafts.csswg.org/cssom/#dom-documentorshadowroot-adoptedstylesheets), [MDN API details](https://developer.mozilla.org/en-US/docs/Web/API/ShadowRoot/adoptedStyleSheets)).

There are important boundaries to preserve:

- Shadow-tree styles are scoped; document rules do not simply pierce the boundary. Rules targeting a custom element’s exposed `::part(...)` are intended to be authored outside that element’s shadow tree. Keep the ordinary document stylesheet link as well as the shadow-root adoption path; do not assume that copying CSS into a root alone replaces outer-document `::part` styling ([CSS Shadow Module](https://drafts.csswg.org/css-shadow-1/), [CODA’s existing CSS selectors and adoption code](src/coda/apps/static/js/global-styles.js)).
- daisyUI’s default theme variables target `:root`. Its documented `root` configuration accepts a selector and explicitly calls out scoping daisyUI into a web component or Shadow DOM; use this if a component needs a locally scoped theme, and confirm whether the app-wide root theme or a component-local theme is desired ([daisyUI configuration](https://daisyui.com/docs/config/)).
- `global-styles.js` reads each sheet’s `cssRules` without catching errors. CSSOM specifies that `cssRules` throws `SecurityError` when the stylesheet is not origin-clean. Thus an opaque cross-origin stylesheet can interrupt the adoption pass; the generated local stylesheet is same-origin, but all other linked sheets encountered by the loop remain a compatibility concern ([CSSOM `cssRules`](https://drafts.csswg.org/cssom/#dom-cssstylesheet-cssrules), [CODA stylesheet adoption](src/coda/apps/static/js/global-styles.js)).

## Compatibility risks to resolve during adoption

1. **Browser baseline:** Tailwind v4.0 targets Safari 16.4+, Chrome 111+, and Firefox 128+, and depends on modern CSS features including `@property` and `color-mix()`. If supported browsers include older versions, Tailwind recommends remaining on v3.4 instead of v4 ([Tailwind upgrade guide](https://tailwindcss.com/docs/upgrade-guide)).
2. **Existing CSS and reset behavior:** `@import "tailwindcss"` includes Preflight, which resets margins/padding, border defaults, heading typography, and list markers. CODA currently has Pico plus many app CSS files, so check cascade/order and existing typography, list, and form assumptions before replacing or layering styles; Tailwind documents that Preflight can be omitted when integrating with an existing project ([Tailwind Preflight](https://tailwindcss.com/docs/preflight); current shell: `src/coda/apps/templates/base.html`).
3. **Shadow-root semantics and timing:** The current code copies every `document.styleSheets` rule list when it first builds its cached global sheets. Keep the generated CSS link in the document and ensure it has loaded before the first adoption. Check utility selectors and daisyUI theme variables inside each custom element’s actual shadow tree, while preserving document-level `::part` rules. CSSOM’s origin-clean restriction applies to each sheet in that enumeration ([CODA adoption implementation](src/coda/apps/static/js/global-styles.js), [CSSOM](https://drafts.csswg.org/cssom/#dom-cssstylesheet-cssrules), [CSS Shadow Module](https://drafts.csswg.org/css-shadow-1/)).
4. **Reproducible compiler artifacts:** Tailwind standalone is an OS/architecture-specific executable, and daisyUI’s no-Node route also relies on the matching daisyUI bundle. Pin compatible versions in the build process and keep the executable and plugin version paired; use a controlled artifact source rather than unpinned “latest” downloads ([Tailwind standalone CLI](https://tailwindcss.com/docs/installation/tailwind-cli), [daisyUI Django guide](https://daisyui.com/docs/install/django/)).
